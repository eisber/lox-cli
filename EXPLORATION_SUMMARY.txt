KEY FINDINGS
================================================================================

1. ENGINE ARCHITECTURE
   ✓ Signal-based: signals[ConnectorId] = f64 value
   ✓ Dirty-flag optimized: blocks skipped if inputs unchanged
   ✓ Topologically ordered: all upstream blocks eval before downstream
   ✓ Feedback-aware: back-edges use prev_signals[] to prevent cycles

2. CORE FIELDS
   • signals: Vec<f64> - current connector values
   • prev_signals: Vec<f64> - previous-tick snapshot
   • dirty: Vec<bool> - per-block dirty flags
   • downstream: Vec<Vec<BlockId>> - adjacency for dirty propagation
   • named_inputs/named_outputs: name→cid lookup maps

3. TICK ALGORITHM (tick() method, lines 265-387)
   FOR each block in topological order:
     IF dirty[block]:
       inputs = gather(signals[] or prev_signals[] if feedback)
       params = gather(signals[param_cids])
       prev_inputs = gather(prev_signals[input_srcs])
       outputs = block.eval(inputs, params, dt, prev_inputs)
       FOR output in outputs:
         IF value_changed: mark_downstream_dirty()
       dirty[block] = false
   
   AFTER loop:
     prev_signals[] = signals[]  // Snapshot for next tick
     FOR edge_sensitive blocks:
       IF their prev_inputs context changed:
         dirty[block] = true

4. VALUE INJECTION METHODS
   set_input(name, value)
   ├─ Targets: input connectors or source block outputs
   ├─ Effect: signals[cid] = value; dirty[block] = true
   └─ Special: If OUTPUT connector, also mark downstream dirty
   
   inject_output(name, value)
   ├─ Targets: output connectors directly
   ├─ Effect: signals[cid] = value; dirty[block] = true; mark downstream
   └─ Use case: Simulate sensor readings
   
   set_param(block, key, value)
   ├─ Targets: parameter connectors only
   └─ Effect: signals[cid] = value; dirty[block] = true

5. BLOCK TRAIT (Block::eval)
   fn eval(inputs, params, dt, prev_inputs) → Vec<Signal>
   ├─ inputs: current-tick values from connected inputs
   ├─ params: current-tick values from parameter connectors
   ├─ dt: time delta (not always used)
   ├─ prev_inputs: previous-tick input values (for edge detection)
   └─ Returns: one f64 per output connector
   
   Special method: is_edge_sensitive() → bool
   └─ If true, block re-marked dirty if prev_inputs context changed
   └─ Used by: RisingEdge, Counter, OffDelay, etc.

6. GRAPH STRUCTURE
   • ConnectorId = usize (index into global signals array)
   • BlockId = usize (index into blocks array)
   • BlockInfo: { id, name, room, inputs, outputs, params }
   • ConnectorInfo: { id, key, dir, block_id, default_value }
   • input_source: Map[input_cid] → output_cid (the wire)
   • Topological sort identifies feedback wires (back-edges)

7. SOURCE BLOCKS (SysVar, VirtualIn)
   Special treatment in engine:
   ├─ Type-checked as "source_types = ["SysVar", "VirtualIn"]"
   ├─ Bare name maps to BOTH inputs AND outputs
   ├─ set_input("VirtualIn", 5.0) drives output directly
   ├─ Output connector changes mark downstream dirty
   └─ Allows injection to propagate immediately

8. DIRTY FLAG STRATEGY
   dirty[block] = true when:
   ├─ set_input(), inject_output(), or set_param() called
   ├─ Upstream block's output changes (> ε difference)
   ├─ Edge-sensitive block's prev_inputs context changes
   └─ mark_all_dirty() called explicitly
   
   dirty[block] = false after:
   └─ Block successfully evaluated

9. NAMED INPUTS/OUTPUTS RESOLUTION
   Bare name:              "BlockName"
   Dotted name:            "BlockName.ConnectorKey"
   Room-qualified bare:    "BlockName [RoomName]"
   Room-qualified dotted:  "BlockName [RoomName].ConnectorKey"
   
   For source blocks: bare name maps to ALL inputs AND outputs
   For normal blocks:  bare name maps to first input (set_input) or first output (get_output)

10. FEEDBACK LOOPS
    Identified via topological sort back-edge detection
    eval_info[block].input_sources = [(src_cid, is_feedback), ...]
    IF is_feedback: read prev_signals[src] ELSE read signals[src]
    Prevents same-tick cycles; feedback delayed by one tick

11. NO EXISTING FREEZE MECHANISM
    ✗ No way to hold output constant without block re-eval
    ✗ No way to prevent block from overwriting overridden value
    ✗ No way to "freeze" a block mid-simulation
    ✗ No tracking of where override came from
    ✗ No priority system for conflicting overrides

================================================================================
GAP ANALYSIS: LIMITATION OF CURRENT VALUE INJECTION
================================================================================

PROBLEM 1: One-shot overrides are overwritten
─────────────────────────────────────────────
set_input("Sensor", 5.0)   ← Set value
tick(0.01)
  Block evaluates → outputs new_value
  signals[cid] = new_value   ← OVERWRITES injected 5.0
Result: Next tick, old injected value is gone

PROBLEM 2: No persistent hold mechanism
──────────────────────────────────────
Cannot simulate:
├─ Frozen hardware output (e.g., valve stuck open)
├─ Faulty sensor (reading always same value)
├─ Emergency shutdown (output forced to 0)
└─ Testing: hold output while varying inputs

PROBLEM 3: No override context/metadata
─────────────────────────────────────────
Cannot determine:
├─ Is this value overridden?
├─ Why is it overridden?
├─ When was it overridden?
├─ What override source has priority?

PROBLEM 4: No conflict resolution
──────────────────────────────────
Multiple systems may want to override same connector
└─ No priority system to resolve conflicts

================================================================================
PROPOSED SOLUTION: OVERRIDE REGISTRY
================================================================================

Add to SimEngine:
  overrides: HashMap<ConnectorId, OverrideState>
  tick_counter: u64

pub enum OverrideState {
    Snapshot { value: f64, tick_set: u64 },           // 1-tick override
    Held { value: f64, source: String, locked_at_tick: u64 },  // Persistent
}

New API Methods:
1. inject_snapshot(name, value) → bool
   └─ One-shot: override lasts exactly 1 tick, then auto-cleared

2. hold_value(name, value, source) → bool
   └─ Persistent: override persists until release_value() called

3. release_value(name) → bool
   └─ Clear override and force block re-evaluation

4. is_overridden(name) → bool
   └─ Query whether a connector has active override

5. get_override(name) → Option<(source, value)>
   └─ Inspect which override is active and its source

6. clear_all_overrides() → void
   └─ Clear all overrides at once (cleanup)

Modified tick():
  FOR each block:
    IF output_cid is overridden: SKIP writing eval result
    ELSE: signals[output_cid] = eval_result
  
  Clear expired snapshots (tick_set < current_tick)

USAGE EXAMPLES
================================================================================

Example 1: Simulate Sensor Failure
───────────────────────────────────
engine.hold_value("Room1.Temperature", 20.0, "sensor_fault");
for tick in 0..100 {
    engine.tick(0.01);
    // Downstream blocks see constant 20.0
}
engine.release_value("Room1.Temperature");
engine.tick(0.01);  // Resume normal operation

Example 2: One-Off Test Stimulus
─────────────────────────────────
engine.inject_snapshot("PresenceDetector.OutputPresence", 1.0);
engine.tick(0.01);  // Motion signal processed
// Snapshot automatically cleared before next tick
engine.tick(0.01);  // No motion

Example 3: Emergency Shutdown
──────────────────────────────
if building_on_fire {
    engine.hold_value("System.MainRelay", 0.0, "emergency");
}
// Cannot override until emergency is cleared

Example 4: Debug Value Freezing
────────────────────────────────
for tick in 0..1000 {
    engine.tick(0.01);
    if engine.get_output("House.Temperature") > 30.0 {
        engine.hold_value("HeatController.Output", 0.0, "debug_freeze");
        // Investigate with heating frozen...
        break;
    }
}

================================================================================
PERFORMANCE IMPACT
================================================================================

Memory:
  - HashMap<ConnectorId, OverrideState>
  - Typical: < 1KB for most simulations
  - Worst case: O(number of overridden connectors)

CPU:
  - Lookup: O(1) amortized per output
  - Insertion/removal: O(1) amortized
  - Negligible impact on tick() runtime
  - Clearing snapshots: O(number of active overrides)

Trade-off: Minimal overhead for significant capability gain.

================================================================================
RISK ASSESSMENT
================================================================================

Risk: Overrides prevent block state from advancing
──────────────────────────────────────────────────
Mitigation: Override only output signals, not internal state
Result: Block state continues to advance; output just bypassed

Risk: Multiple overrides on same connector
──────────────────────────────────────────
Mitigation: HashMap allows only one override per connector
Future:    Could add priority system if needed

Risk: Forgotten overrides affecting subsequent tests
───────────────────────────────────────────────────
Mitigation: clear_all_overrides() + test harness documentation
Future:    Add test cleanup fixtures
